# مهام مطور Backend (Laravel) — سوق متعدد التجار

> **الحالة الحالية للكود:** Laravel 10 + Breeze + Sanctum. يوجد فعلياً: نماذج `User` / `Store` / `Category` / `Product` مع `StoreScope` لعزل بيانات التاجر، وCRUD في لوحة التحكم للأقسام (مع Soft Deletes وسلة محذوفات) والمتاجر والمنتجات. **ابنِ فوق الموجود ولا تعد كتابته من الصفر.**
>
> **قواعد عامة إلزامية:**
> - كل منطق مالي (عمولات، أرصدة، ضرائب، مرتجعات) داخل **Service Classes** مغطاة باختبارات PHPUnit — ليس داخل الـ Controllers.
> - كل عملية متعددة الخطوات (إنشاء طلب، تقسيمه، خصم مخزون) داخل **DB Transaction**.
> - المبالغ المالية تُخزّن `decimal(12,2)` (أو بالهللات كأعداد صحيحة) — ممنوع `float`.
> - كل جدول جديد يُوثّق قراره في Migration واضحة، وكل نظام له Seeder لبيانات تجريبية.
> - الالتزام بـ Laravel Pint (متوفر في المشروع) قبل كل Push.

## المرحلة 0 — التأسيس (سبرنت 0)

- [ ] مراجعة الكود الحالي وكتابة ملاحظات إعادة الهيكلة (مثلاً: مراجعة `StoreScope` وتأثيره عند دخول الأدمن).
- [ ] إعداد بيئة Staging + نشر تلقائي من فرع `develop` (deploy script أو GitHub Actions).
- [ ] إعداد GitHub Actions لتشغيل الاختبارات وPint على كل Pull Request.
- [ ] **تصميم مخطط قاعدة البيانات الكامل (ERD)** للأنظمة القادمة كلها — خاصة: المنتجات/الـ Variants، الطلبات/sub-orders، العمولات/المحافظ — ومراجعته مع مدير المشروع قبل M2. هذا أهم مخرج في هذه المرحلة لأن تعديله لاحقاً مكلف.
- [ ] تثبيت الحزم الأساسية: `spatie/laravel-permission`، `spatie/laravel-medialibrary` (أو نظام صور بسيط)، `barryvdh/laravel-dompdf` (فواتير)، `spatie/laravel-translatable` أو جداول ترجمة (قرار يُتخذ هنا).

## المرحلة 1 — الحسابات والصلاحيات (M1)

- [ ] دمج `spatie/laravel-permission`: أدوار admin / manager / vendor / customer + Seeder للصلاحيات.
- [ ] Middleware وGates للوحات: `admin.*` للأدمن/المدير، `vendor.*` للتاجر — وإعادة تنظيم `routes/dashboard.php` إلى `routes/admin.php` و`routes/vendor.php`.
- [ ] تدفق تسجيل التاجر: طلب انضمام (جدول `vendor_applications` أو حالة على `stores`) ← مراجعة الأدمن ← تفعيل المتجر وإنشاء دور vendor.
- [ ] ضبط `StoreScope` بحيث لا يقيّد الأدمن، ويقيّد التاجر بمتجره فقط (اختبارات على العزل إلزامية).
- [ ] الترجمة: هيكلة `lang/ar` و`lang/en` + Middleware للغة + ترجمة محتوى الأقسام والمنتجات (حقول JSON عبر spatie/translatable).
- [ ] نظام إعدادات عام للمنصة (`settings` جدول key/value مع Cache): سيُستخدم لاحقاً للعمولة الافتراضية، مدة تحويل الرصيد، الضريبة…
- [ ] API Auth عبر Sanctum (تسجيل/دخول للعميل) تمهيداً لأي تطبيق جوال مستقبلي.

## المرحلة 2 — الكتالوج المتقدم والمخزون (M2)

**المنتجات:**
- [ ] توسيع مخطط المنتجات: `attributes` (لون/مقاس…)، `attribute_values`، `product_variants` (SKU، سعر، سعر جملة، مخزون لكل Variant)، `product_images`.
- [ ] نوع البيع في المنتج: `retail` / `wholesale` / `both` مع حقول: سعر الجملة، الحد الأدنى لكمية الجملة.
- [ ] المنتجات متعددة الأجزاء (Bundles): جدول ربط منتج ← مكوناته، وخصم مخزون المكونات عند البيع.
- [ ] Slugs عربية/إنجليزية وحقول SEO (meta title/description) للمنتج والقسم.

**المخزون:**
- [ ] `stock_movements`: سجل لكل حركة (بيع، مرتجع، تعديل يدوي بسبب، إدخال) — المخزون الحالي محسوب أو مخزّن مع تحديث ذري (`lockForUpdate`).
- [ ] حدود التنبيه (أدنى/أقصى) لكل منتج/Variant + Job يرسل تنبيهات للتاجر (بريد + إشعار داخلي) عند التجاوز.

**واجهة المتجر العام (Storefront Backend):**
- [ ] Controllers/Queries للمتجر العام: الرئيسية، القسم مع فلترة (سعر/تاجر/خيارات) وترتيب، صفحة المنتج، صفحة التاجر، البحث (بداية بـ `LIKE`/Full-text، وترقية لاحقة لـ Meilisearch/Scout إن لزم).
- [ ] Eager loading وفهارس قاعدة بيانات مناسبة من البداية (تجنّب N+1).

## المرحلة 3 — السلة والطلبات والدفع (M3) — أثقل مرحلة Backend

**السلة والأمنيات:**
- [ ] سلة للزائر (session/cookie) وللمسجّل (جدول `carts`/`cart_items`) مع دمج عند تسجيل الدخول.
- [ ] تحقق السلة: توفر المخزون، حدود الجملة، إعادة تسعير عند تغير الأسعار. Wishlist بسيطة.

**الطلبات وSplit Orders:**
- [ ] مخطط الطلبات: `orders` (الطلب الأم: العميل، العنوان، الإجماليات، الدفع) + `sub_orders` (لكل تاجر: حالته، شحنه، إجماليه) + `order_items` (مرتبطة بـ sub_order وvariant، مع لقطة سعر واسم وقت الشراء).
- [ ] `CheckoutService`: يبني الطلب من السلة داخل Transaction — تقسيم لكل تاجر، حساب الشحن لكل sub-order، حساب VAT، خصم المخزون، تطبيق الكوبونات (لاحقاً).
- [ ] آلة حالات الطلب (Status flow): pending → paid → processing → shipped → delivered → (cancelled/refunded) لكل sub-order، مع سجل تغييرات الحالة ومن غيّرها.
- [ ] الشحن: مناطق شحن وأسعار لكل تاجر أو موحدة (حسب قرار المنتج)، وإدخال رقم تتبع.

**الدفع:**
- [ ] طبقة دفع مجردة (`PaymentGatewayInterface`) بحيث يُضاف مزود جديد دون تعديل منطق الطلبات.
- [ ] تكامل المزود المجمّع (Moyasar / Tap / HyperPay): إنشاء عملية دفع، Callback/Webhook للتأكيد، معالجة الفشل، وتخزين `transactions`.
- [ ] Apple Pay ومدى عبر نفس المزود، ثم تكامل تابي وتمارا (تقسيط) — كل واحد PR مستقل.
- [ ] الدفع عند الاستلام (COD) كخيار قابل للتفعيل من الإعدادات.
- [ ] **قاعدة أمنية:** لا تُخزّن بيانات بطاقات إطلاقاً؛ Webhooks تُتحقق توقيعاتها؛ عمليات الدفع Idempotent.

**الضرائب:**
- [ ] `TaxService`: نسبة VAT من الإعدادات، حساب على مستوى السطر، وتخزين قيمة الضريبة في الطلب والفاتورة.

**الإشعارات الأساسية:**
- [ ] إشعارات بريد (Laravel Notifications + Queue): طلب جديد للتاجر، تأكيد للعميل، تغيّر حالة الشحن.

## المرحلة 4 — العمولات والمحافظ والفوترة والمرتجعات (M4)

- [ ] `CommissionService`: العمولة الافتراضية (إعدادات) ← عمولة القسم ← عمولة التاجر (الأخص يغلب). تُحتسب وتُخزّن على مستوى `order_items` وقت اكتمال الطلب حتى لا تتأثر بتغيير النسب لاحقاً.
- [ ] المحافظ: `wallets` + `wallet_transactions` (قيد مزدوج مبسّط: كل حركة لها مصدر ومرجع). رصيد معلّق يتحول لمتاح بعد مدة قابلة للضبط من الإعدادات (Scheduled Job يومي).
- [ ] طلبات السحب: `payout_requests` بحالات (pending/approved/paid/rejected)، حد أدنى للسحب من الإعدادات، وخصم من الرصيد المتاح عند الموافقة.
- [ ] الفوترة: توليد فاتورة ضريبية PDF للعميل (عربي/إنجليزي، برقم تسلسلي)، وفاتورة عمولة للتاجر، وأرشيف فواتير للإدارة.
- [ ] المرتجعات: `return_requests` بتدفق (طلب العميل ← موافقة تاجر/أدمن ← استلام ← استرداد) مع أثر عكسي على المخزون والمحفظة والعمولة، وتكامل مع بوابة الدفع للاسترداد (Refund API).
- [ ] **اختبارات آلية شاملة لهذه المرحلة كلها** — هذا شرط قبول وليس تحسيناً.

## المرحلة 5 — النمو (M5)

- [ ] الكوبونات: `coupons` (نسبة/مبلغ، حد استخدام كلي ولكل مستخدم، صلاحية، نطاق: منصة/تاجر/قسم/منتج) + تطبيقها في `CheckoutService` وتوزيع أثرها على sub-orders.
- [ ] التقييمات: `reviews` للمنتج والتاجر، مرتبطة بعنصر طلب مُسلّم (شراء موثّق)، بحالة إشراف (pending/approved/rejected)، وتحديث متوسط التقييم بشكل Denormalized.
- [ ] نظام إشعارات موحد: Laravel Notifications بقنوات database + mail + FCM (Push) + SMS (Msegat/Unifonic عبر Driver مخصص)، وتفضيلات إشعارات للمستخدم.
- [ ] التحليلات: Queries/Views مجمعة للوحة الأدمن (مبيعات يومية/شهرية، أفضل منتجات وتجار، أداء الأقسام) وللتاجر (مبيعاته فقط) — مع Cache للتقارير الثقيلة.
- [ ] البنرات والبادجات: `banners` (موضع: رئيسية/قسم، صورة لكل لغة، رابط، جدولة زمنية، ترتيب) + بادجات للمنتجات (جديد/الأكثر مبيعاً/خصم — يدوية وتلقائية).
- [ ] المدونة: `posts` بمحتوى مترجم + تصنيفات + SEO لكل مقال، وsitemap.xml تلقائي وschema.org (Product, Article, Organization).

## المرحلة 6 — التقوية والإطلاق (M6)

- [ ] مراجعة أداء: فهارس، Cache (config/route/view + Redis للجلسات والطوابير)، واختبار حمل أساسي على الرئيسية وصفحة المنتج وCheckout.
- [ ] مراجعة أمان: صلاحيات كل Route، Rate limiting على الدخول وAPI، تحقق Webhooks، حماية رفع الملفات، مراجعة Mass Assignment.
- [ ] بيئة الإنتاج: خادم، SSL، Queue worker (Supervisor)، Scheduler (cron)، نسخ احتياطي يومي لقاعدة البيانات والملفات (`spatie/laravel-backup`)، ومراقبة أخطاء (Sentry/Flare).
- [ ] توثيق تشغيلي: README للنشر، متغيرات `.env`، وإجراءات الطوارئ.

## معايير قبول عمل مطور الـ Backend

- كل PR يمر بالاختبارات وPint على CI قبل الدمج.
- تغطية اختبارات إلزامية للأنظمة المالية: العمولات، المحافظ، تقسيم الطلبات، الضرائب، المرتجعات، والكوبونات.
- لا استعلامات N+1 في الصفحات الرئيسية (تُفحص بـ Laravel Debugbar/Telescope على بيئة التطوير).
- كل نظام جديد له Seeder يتيح للفريق تجربة الميزة ببيانات واقعية فوراً.
- توثيق مختصر لكل Service رئيسية (متى تُستدعى، ماذا تضمن، ماذا ترمي من أخطاء).
