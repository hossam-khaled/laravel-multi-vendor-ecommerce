# الخطة الشاملة لإدارة المشروع — سوق متعدد التجار (Multi-vendor Marketplace)

## 1. نظرة عامة على المشروع

منصة سوق إلكتروني متعدد التجار تتيح لعدة تجار البيع من خلال منصة واحدة، مع لوحات تحكم منفصلة للأدمن والتاجر، ومتجر عام للعملاء، ونظام عمولات وتسويات مالية.

### أدوار المستخدمين
1. **الأدمن (Admin):** إدارة كاملة للمنصة.
2. **المدير (Manager):** صلاحيات إدارية محددة يمنحها الأدمن.
3. **التاجر (Vendor):** إدارة متجره ومنتجاته وطلباته وأرباحه.
4. **العميل (Customer):** التصفح والشراء والتقييم والمرتجعات.

### ما هو منجز فعلياً في المستودع (نقطة البداية)
- Laravel 10 + Breeze (تسجيل دخول/تسجيل/استعادة كلمة مرور) + Sanctum.
- نماذج: `User`, `Store`, `Category`, `Product` مع `StoreScope` لعزل بيانات كل تاجر.
- لوحة تحكم أولية: CRUD للأقسام (مع سلة محذوفات واستعادة)، المتاجر، المنتجات.
- الواجهة: Blade + Tailwind CSS + Alpine.js + Vite.
- **غير منجز:** الطلبات، السلة، الدفع، الصلاحيات، العمولات، المتجر العام للعملاء، وكل ما تبقى في الجدول أعلاه.

## 2. المنهجية والهيكل الزمني

### المنهجية: Agile / Scrum مبسّط
- **سبرنت = أسبوعان.** كل سبرنت له هدف واضح ومخرجات قابلة للعرض (Demo).
- كل ميزة تُدار كـ **User Story** على لوحة مهام (Trello / Jira / GitHub Projects / ClickUp).
- تقدير المهام بنقاط بسيطة (S / M / L) بدل الساعات الدقيقة في البداية.

### المراحل الكبرى (Milestones)

```
M0 التأسيس ──► M1 الأساسات ──► M2 الكتالوج ──► M3 الشراء والدفع ──► M4 المالية ──► M5 النمو ──► M6 الإطلاق
```

#### M0 — التأسيس والتجهيز (سبرنت 0 — أسبوع واحد)
**الهدف:** فريق جاهز، بيئة عمل موحدة، قرارات تقنية محسومة.
- إعداد بيئات التطوير لكل عضو + بيئة Staging.
- إعداد Git workflow (فروع، مراجعة كود، حماية main).
- إعداد لوحة المهام وقنوات التواصل.
- **قرار تقني حاسم يُتخذ هنا:** واجهة المتجر العام — Blade+Alpine (نفس النمط الحالي) أم Vue/Inertia. *التوصية: الاستمرار على Blade + Tailwind + Alpine لتوحيد النمط وتسريع التنفيذ، مع API (Sanctum) جاهز لتطبيق جوال مستقبلاً.*
- UI/UX: بدء البحث والـ Wireframes (يسبق الفريق التقني بسبرنت واحد دائماً).

#### M1 — الأساسات: الحسابات والصلاحيات (سبرنتان)
**الهدف:** أنظمة الحسابات الأربعة تعمل بصلاحيات صحيحة، والمشروع ثنائي اللغة من اليوم الأول.
- نظام الأدوار والصلاحيات (spatie/laravel-permission): أدمن / مدير / تاجر / عميل.
- تسجيل التاجر (مع طلب انضمام وموافقة الأدمن) وتسجيل العميل.
- ملفات المتجر: بيانات المتجر، الشعار، حالة التفعيل.
- تفعيل الترجمة (ar/en) + دعم RTL في القوالب من الآن.
- إعادة هيكلة لوحة التحكم للفصل بين لوحة الأدمن ولوحة التاجر.

**معيار الإنجاز:** أدمن يوافق على تاجر جديد، التاجر يدخل لوحته ويرى بياناته فقط، العميل يسجل ويدخل حسابه.

#### M2 — الكتالوج المتقدم والمخزون (سبرنتان)
**الهدف:** التاجر يضيف منتجات بكل أنواعها والمخزون يتتبع تلقائياً.
- توسيع المنتجات: خيارات وأشكال (Variants: مقاس/لون/…)، منتجات متعددة الأجزاء.
- نوع البيع لكل منتج: جملة / قطعة / مختلط (مع حد أدنى لكمية الجملة وسعر جملة).
- المخزون الذكي: تتبع لكل Variant، تنبيهات الحد الأدنى/الأقصى، سجل حركات المخزون وتعديله يدوياً.
- صور المنتجات المتعددة، والـ SEO الأساسي للمنتج (slug, meta).
- واجهة المتجر العام (Storefront): الرئيسية، صفحة القسم، صفحة المنتج، البحث والفلترة.

**معيار الإنجاز:** عميل يتصفح المتجر ويرى منتجاً بمقاسات وألوان بأسعار جملة وقطعة، والتاجر يستلم تنبيهاً عند انخفاض المخزون.

#### M3 — الشراء: السلة والطلبات والدفع (سبرنتان إلى ثلاثة)
**الهدف:** دورة شراء كاملة من السلة حتى الدفع، مع تقسيم الطلبات.
- السلة (Cart) وقائمة الأمنيات (Wishlist) — للزائر والمسجّل.
- Checkout: العناوين، اختيار الشحن، ملخص الطلب.
- **Split Orders:** الطلب الواحد يتقسم آلياً إلى sub-orders لكل تاجر، بحالة مستقلة لكل sub-order.
- نظام الشحن: مناطق وأسعار شحن، وحالات الطلب (جديد/قيد التجهيز/شُحن/سُلّم/ملغي).
- الضرائب (VAT 15%): محسوبة على مستوى السطر والفاتورة.
- بوابات الدفع: **البدء بمزوّد مجمّع** (مثل Moyasar / Tap / HyperPay) يغطي مدى + البطاقات + Apple Pay، ثم تابي وتمارا، والدفع عند الاستلام (COD).
- إشعارات الطلبات الأساسية (بريد إلكتروني) للعميل والتاجر.

**معيار الإنجاز:** عميل يشتري من تاجرين في طلب واحد، يدفع ببطاقة (بيئة اختبار)، يتقسم الطلب لتاجرين، وكل تاجر يدير sub-order الخاص به.

#### M4 — المالية: العمولات والفوترة والمرتجعات (سبرنتان)
**الهدف:** المنصة تحسب أرباحها وأرباح التجار بدقة.
- محرك العمولات: عمولة افتراضية عامة، وتخصيص لكل قسم ولكل تاجر (الأولوية: تاجر ← قسم ← افتراضي).
- محفظة التاجر: أرصدة (معلّق / متاح)، مع مدة تحويل الرصيد قابلة للضبط في الإعدادات.
- طلبات سحب الأرباح للتاجر وموافقة الأدمن عليها.
- الفوترة: فاتورة العميل، فاتورة عمولة المنصة للتاجر، تقارير فوترة للإدارة (PDF).
- المرتجعات: طلب إرجاع، سير موافقة، تتبع حالة المرتجع، وأثره على المخزون والمحفظة والعمولة.

**معيار الإنجاز:** طلب مكتمل يولّد عمولة صحيحة ورصيداً للتاجر، التاجر يطلب سحباً والأدمن يوافق، ومرتجع يعكس المبالغ بشكل صحيح.

#### M5 — النمو: العروض والتقييمات والإشعارات والتحليلات (سبرنتان)
- كوبونات الخصم والعروض (نسبة/مبلغ ثابت، حد استخدام، تاريخ صلاحية، على مستوى المنصة أو التاجر).
- التقييمات والمراجعات (منتج + تاجر) مع إشراف الأدمن، ولا تقييم إلا بعد شراء فعلي.
- الإشعارات الفورية: Push (Firebase) + SMS (مزود محلي مثل Msegat/Unifonic) + Email — عبر نظام إشعارات موحد.
- لوحة التحليلات والتقارير: مبيعات، أفضل المنتجات/التجار، تقارير مالية، تقارير مخزون.
- البنرات والبادجات في الرئيسية وصفحات الأقسام (إدارة من لوحة الأدمن).
- نظام المقالات/المدونة + تحسينات SEO (sitemap، schema.org، meta، روابط عربية).

#### M6 — التقوية والإطلاق (سبرنت واحد إلى سبرنتين)
- اختبارات شاملة (وظيفية + أداء + أمان) وإصلاح الأخطاء.
- تجربة مستخدم نهائية على الجوال (معظم الزوار جوال).
- تجهيز بيئة الإنتاج، النسخ الاحتياطي، المراقبة (logs, uptime).
- إطلاق تجريبي (Soft Launch) بعدد محدود من التجار ثم الإطلاق العام.

> **ملاحظة على المدة الإجمالية:** بفريق من 3 منفّذين، المسار أعلاه يعادل تقريباً 12–16 سبرنت-أسبوع عمل فعلي (حوالي 5–7 أشهر تقويمية بدوام كامل). يمكن الضغط بتقليص نطاق MVP (مثلاً تأجيل تابي/تمارا والمدونة والتحليلات المتقدمة لما بعد الإطلاق).

## 3. مصفوفة المسؤوليات (RACI مبسّطة)

| مجال العمل | UI/UX | Backend | Frontend | مدير المشروع |
|---|---|---|---|---|
| متطلبات وأولويات | يُستشار | يُستشار | يُستشار | **مسؤول وقرار** |
| تصميم الواجهات والتجربة | **مسؤول** | يُستشار | يُستشار | يعتمد |
| قاعدة البيانات وواجهات API | يُطّلع | **مسؤول** | يُستشار | يعتمد |
| منطق الأعمال (طلبات/عمولات/دفع) | — | **مسؤول** | يُطّلع | يعتمد |
| تنفيذ الواجهات (Blade/Tailwind/Alpine) | يراجع المطابقة | يُستشار | **مسؤول** | يعتمد |
| تكامل بوابات الدفع | — | **مسؤول** | يساند (واجهة الدفع) | يعتمد |
| الترجمة والـ RTL | يوجّه | يساند (ملفات lang) | **مسؤول** | يعتمد |
| الاختبار والجودة | يختبر التجربة | اختبارات آلية | اختبار المتصفحات | **مسؤول القبول** |
| النشر والإنتاج | — | **مسؤول** | يساند | يعتمد |

## 4. إدارة المخاطر

| الخطر | الاحتمال | الأثر | خطة التخفيف |
|---|---|---|---|
| تعقيد Split Orders والعمولات يؤخر M3/M4 | عالٍ | عالٍ | تصميم مخطط قاعدة البيانات كاملاً في M1 ومراجعته قبل التنفيذ؛ اختبارات آلية للحسابات المالية إلزامية |
| تأخر الموافقات على بوابات الدفع (تابي/تمارا تتطلب سجلاً تجارياً وعقوداً) | عالٍ | متوسط | بدء إجراءات التسجيل لدى مزودي الدفع منذ M0 بالتوازي؛ الإطلاق ممكن بمزوّد مجمّع + COD |
| اكتشاف متطلبات RTL/ترجمة متأخراً يعيد فتح شاشات منجزة | متوسط | عالٍ | إلزام ثنائية اللغة وRTL من M1 في كل شاشة جديدة (ضمن تعريف الإنجاز) |
| توسّع النطاق (Scope Creep) أثناء التنفيذ | عالٍ | عالٍ | أي ميزة جديدة تدخل Backlog ولا تدخل السبرنت الجاري؛ التغيير يُقيّم أثره قبل الالتزام |
| اعتماد Frontend على تصاميم غير جاهزة | متوسط | متوسط | UI/UX يسبق التنفيذ بسبرنت كامل دائماً؛ تسليم التصاميم شرط لبدء المهمة |
| مغادرة أحد أعضاء الفريق | منخفض | عالٍ | توثيق مستمر (README لكل نظام)، مراجعة كود إلزامية تضمن معرفة مشتركة |
| ثغرات أمنية في الدفع والأموال | متوسط | حرج | عدم تخزين بيانات بطاقات إطلاقاً (Tokenization من المزود)، مراجعة أمنية قبل الإطلاق، صلاحيات صارمة |

## 5. تعريف الإنجاز (Definition of Done)

مهمة لا تُعتبر منجزة إلا إذا:
1. تعمل وظيفياً حسب وصف الـ User Story ومعايير القبول.
2. تدعم العربية والإنجليزية وتعرض سليمة في وضع RTL.
3. متجاوبة على الجوال والتابلت والديسكتوب.
4. مرّت بمراجعة كود (Pull Request معتمد من عضو آخر).
5. الحسابات المالية والمخزون مغطاة باختبارات آلية (PHPUnit).
6. مدمجة في فرع `develop` وتعمل على بيئة Staging.
7. لا تكسر أي ميزة قائمة.
