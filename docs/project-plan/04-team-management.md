# دليل إدارة الفريق وسير العمل

هذا الدليل يحدد كيف يعمل الفريق يومياً وأسبوعياً، وكيف تُدار المهام والجودة والتواصل. الهدف: أقل قدر من الاجتماعات، وأكبر قدر من الوضوح والمساءلة.

## 1. تشكيلة الفريق والأدوار

| الدور | المسؤولية الأساسية | يرفع تقاريره إلى |
|---|---|---|
| مدير المشروع / مالك المنتج (أنت) | الأولويات، القرارات، قبول المخرجات، التواصل مع مزودي الدفع والاستضافة | — |
| مصمم UI/UX | التصاميم والتجربة، Design System، مراجعة المطابقة | مدير المشروع |
| مطور Backend (Laravel) | قاعدة البيانات، منطق الأعمال، الدفع، الأداء، النشر | مدير المشروع |
| مطور Frontend | تنفيذ الواجهات (Blade/Tailwind/Alpine)، RTL والترجمة، تجربة الجوال | مدير المشروع |

**قاعدة التسلسل:** التصميم يسبق الـ Frontend بسبرنت، والـ Backend يجهّز الـ API/البيانات قبل أو بالتوازي مع تنفيذ الواجهة. عند التعطيل المتبادل: Backend يسلّم عقد البيانات (أسماء الحقول والمسارات) مبكراً ليعمل Frontend ببيانات وهمية.

## 2. إيقاع العمل (Cadence)

| الطقس | التوقيت | المدة | المحتوى |
|---|---|---|---|
| Daily Standup (كتابي يُفضّل) | يومياً صباحاً | 5 دقائق | كل عضو يكتب في القناة: ماذا أنجزت أمس؟ ماذا ستعمل اليوم؟ هل يوجد معيق؟ |
| Sprint Planning | أول يوم في السبرنت | ساعة | اختيار مهام السبرنت من الـ Backlog وتقديرها والاتفاق على هدف السبرنت |
| Sprint Review (Demo) | آخر يوم في السبرنت | 45 دقيقة | عرض حي لما أُنجز على Staging — ما لا يُعرض لا يُعتبر منجزاً |
| Retrospective | بعد الـ Review مباشرة | 15 دقيقة | ما الذي نجح؟ ما الذي نحسّنه؟ قرار تحسين واحد على الأقل |
| مزامنة تصميم/تنفيذ | منتصف السبرنت | 30 دقيقة | المصمم + Frontend: مراجعة المطابقة والشاشات القادمة |

**قواعد التواصل:**
- المعيقات (Blockers) تُرفع فوراً في القناة ولا تُترك للاجتماع اليومي.
- أي قرار يُتخذ في نقاش صوتي يُلخّص كتابياً في لوحة المهام أو القناة.
- زمن الرد المتوقع داخل ساعات العمل: 3 ساعات كحد أقصى للأسئلة المعطِّلة.

## 3. لوحة المهام وإدارة الـ Backlog

**الأداة:** GitHub Projects (موصى بها لارتباطها بالكود) بأعمدة:

```
Backlog ← جاهزة للتنفيذ (Ready) ← قيد التنفيذ ← مراجعة (PR/Design Review) ← اختبار على Staging ← منجزة
```

**قواعد اللوحة:**
- كل مهمة لها: وصف، معايير قبول، مرحلة (M1..M6)، مُكلَّف واحد، وتقدير (S/M/L).
- المهمة لا تدخل "جاهزة للتنفيذ" إلا إذا كان تصميمها معتمداً (للواجهات) ومتطلباتها واضحة.
- لا يعمل العضو على أكثر من مهمتين "قيد التنفيذ" في نفس الوقت.
- مدير المشروع وحده ينقل المهام إلى "منجزة" (بعد فحص معايير القبول على Staging).
- أي فكرة أو طلب جديد يذهب إلى Backlog ويُرتّب في الـ Planning القادم — لا مقاطعة للسبرنت الجاري إلا للأعطال الحرجة.

## 4. سير عمل Git والمراجعة

**الفروع:**

```
main        ← الإنتاج فقط (محمي، لا يُدفع إليه مباشرة)
develop     ← فرع التكامل، يُنشر تلقائياً على Staging
feature/*   ← فرع لكل مهمة (feature/vendor-registration, fix/cart-total)
```

**القواعد:**
1. كل مهمة = فرع = Pull Request واحد صغير قدر الإمكان (يُفضّل أقل من 400 سطر تغيير).
2. لا دمج بدون مراجعة عضو آخر: Backend وFrontend يتبادلان المراجعة؛ ومدير المشروع يراجع الحساسة (دفع/عمولات).
3. CI (اختبارات + Pint) يجب أن يمر قبل الدمج.
4. رسائل Commit وصفية بالإنجليزية: `feat: split order into sub-orders per vendor`.
5. الدمج إلى `main` يتم فقط في نهاية المرحلة بعد اختبار Staging، ويُوسم بإصدار (v0.1, v0.2…).

**مراجعة التصميم:** واجهات المراحل الحرجة تمر بخطوة "Design Review" يتحقق فيها المصمم من المطابقة قبل اعتبار المهمة منجزة.

## 5. الجودة والاختبار

- **Backend:** اختبارات PHPUnit إلزامية للمنطق المالي والطلبات والمخزون؛ تعمل تلقائياً على كل PR.
- **Frontend:** فحص يدوي على جوال + ديسكتوب، عربي + إنجليزي، مع لقطات شاشة في الـ PR.
- **اختبار القبول:** مدير المشروع يختبر كل ميزة على Staging مقابل معايير القبول قبل الإغلاق.
- **جولة اختبار شاملة (Regression)** في نهاية كل مرحلة على التدفقات الحرجة: تسجيل ← إضافة منتج ← شراء ← تقسيم طلب ← عمولة.
- **سجل الأخطاء:** الأخطاء تُسجّل كمهام بأولوية (حرج: يُصلح فوراً / عالي: داخل السبرنت / عادي: Backlog).

## 6. متابعة التقدم والتقارير

- **مؤشر التقدم الأساسي:** نسبة إنجاز مهام المرحلة الحالية + عدد المهام المنجزة فعلياً كل سبرنت (Velocity) — بعد 2–3 سبرنتات تصبح التوقعات الزمنية واقعية.
- **تقرير أسبوعي مختصر** (يكتبه مدير المشروع من اللوحة): ما أُنجز، ما تأخر ولماذا، قرارات مطلوبة، المخاطر المستجدة.
- **إشارات إنذار مبكر تستدعي تدخلاً:** مهمة "قيد التنفيذ" أكثر من 4 أيام دون تحديث؛ PR مفتوح أكثر من يومين دون مراجعة؛ عضو لم يعرض شيئاً في Demo سبرنتين متتاليين.

## 7. مسؤوليات مدير المشروع خارج الفريق (تبدأ مبكراً)

هذه بنود لا يستطيع الفريق التقني إنجازها وتُعطّل الإطلاق إن تأخرت:

- [ ] فتح حسابات مزودي الدفع (المزود المجمّع + تابي + تمارا) — تتطلب سجلاً تجارياً وحساباً بنكياً وقد تستغرق أسابيع للموافقة. **تبدأ في M0.**
- [ ] حساب مزود SMS (Msegat/Unifonic) وقالب اسم المرسِل (Sender Name) المعتمد.
- [ ] الدومين والاستضافة (خادم Staging مبكراً، وخادم إنتاج قبل M6) وبريد إرسال (SES/Mailgun…).
- [ ] الصفحات القانونية: الشروط والأحكام، سياسة الاسترجاع، الخصوصية، واتفاقية التاجر (تحتاج صياغة قانونية).
- [ ] تحديد سياسات العمل التي يبني عليها الفريق: نسبة العمولة الافتراضية، مدة تحويل الرصيد، الحد الأدنى للسحب، سياسة الشحن (موحد أم لكل تاجر)، نسبة VAT.
- [ ] تجهيز تجار حقيقيين (5–10) للإطلاق التجريبي ومحتواهم (منتجات وصور).

## 8. مبادئ حاسمة للنجاح

1. **الشاشة غير المكتملة خير من النظام غير المكتمل:** أطلقوا كل مرحلة كاملة تعمل بدلاً من فتح كل الأنظمة معاً.
2. **ثنائية اللغة ليست مرحلة أخيرة:** أي شاشة تُقبل بلغة واحدة سيعاد فتحها لاحقاً بتكلفة أعلى.
3. **المال لا يُختبر يدوياً فقط:** أي كود يلمس العمولات أو الأرصدة بلا اختبار آلي هو دين تقني خطير.
4. **الـ Demo هو الحقيقة:** التقدم يقاس بما يعمل على Staging، لا بما يُقال إنه "شبه جاهز".
5. **قرارات المنتج تُحسم قبل التنفيذ لا أثناءه:** كل غموض في المتطلبات يُحل مع مدير المشروع قبل بدء المهمة.
